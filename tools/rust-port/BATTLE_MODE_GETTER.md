# Preserving the real battleEngine accessor

The first full controller A/B exposed a domain mismatch: enabling the previous shortcut produced only 161 hits from 50,462 attempts. The shipped `ed.battleEngine` property is an accessor; the earlier raw-data guard rejected it. Those sparse hits do not establish useful hot-path coverage, and the earlier ~2% full-battle timing difference is not a meaningful optimization result.

This candidate pins the exact 122-character getter from game_battle.js, SHA256 `93ba986430208c8a8258a1ec7345d52d877345ddada92b898f2b39d7baa6cca9`. It accepts only the warmed path with an ordinary namespace receiver, its original prototype, the exact getter source, and an own data `_battleEngineInstance` containing an object. Config/mode, table/parser/ID helpers and all later inputs retain their original preflight guards. The cold constructor branch and any getter/coercion/opaque-helper uncertainty fall back to the original predicate before any candidate source call.

The actual getter still executes twice before the first table call and, for a matching mode, a third time before getBattleId. The setter is never invoked. Actual accepted helper entry order is `G G T G B T`; an absent mode produces `G G T T`. New `battle_mode_limit_domain_hits` excludes the trivial falsy-input shortcut, and `battle_mode_limit_getter_calls` counts getter invocations performed by the accepted predicate path.

Validation: 93 native tests pass, including exact getter/table/ID order, no setter calls, late-helper/cold-instance rejection before getter calls, and 69 actual getters across 23 actual GC safepoints. The differential source gate matches 98 covered OFF/ON observations; two additional active `.caller` cases retain the explicitly documented preexisting baseline limitation. New source cases cover warmed/cold getters, instance accessors, late opaque ID callbacks, active arguments, instance replacement and an unused shadowed constructor binding.

The paired controller fixture installs the actual getter and uses the shipped configuration across eight changing gameplay inputs. Every 2,000-call trial preserves exactly 5,750 actual getter entries, 4,000 table entries, 1,750 battle-ID entries and the same 11,500-entry ordered `G/T/B` trace as Node. Complete result/state bits and function source metadata match. Three trials measured 42,921 → 83,384 calls/sec (1.943×), with only pure transient parser/split work elided. Evidence: `benchmarks/results/2026-10-29T00-51-11.579Z-rust-battle-mode-getter.json`.

The short timing process may have overlapped another one-job compiler before its pause request was received. Treat the timing as component evidence, not a precise isolated throughput result. Full battle parity and nontrivial domain admission must be measured after integration; the isolated runtime's outer flag remains OFF by default.
